# Freddai implementation instructions

- Preserve existing behavior and user-owned work. Trace the actual runtime path before changing code; distinguish confirmed evidence from assumptions.
- Treat every requested application update as a cross-platform update by default: keep macOS, iPhone/iOS, every physical iPad/iPadOS, and Android current without requiring the user to name each platform or device. Trace the equivalent runtime paths in shared web UI and each native shell; implement applicable behavior on every platform and adapt layout to screen size. A change made in an iPad-specific view is not complete while the corresponding iPhone or Android experience is stale. Only narrow platform/device scope when the user explicitly requests it; do not infer a platform-only exception from the file edited or device mentioned.
- For every application change, run appropriate checks, rebuild the macOS app, sign it using the user's existing Developer ID, and reinstall it in `/Applications/Freddai.app` before reporting delivery. Use `pnpm native:install` for the repeatable build/sign/install path. A source edit or browser preview alone is not delivery.
- For application updates, also rebuild and sign the companion app using the existing Apple development signing setup, install the updated build on the user's iPhone and every physical iPad they own (currently DiPhone, 2021 iPad Pro 12, and 2022 iPad mini), and relaunch and verify the updated app on each device before reporting delivery. Use `pnpm ios:install` with `FREDDAI_IOS_DEVICE` set explicitly for each intended paired device; Discover the current paired physical-device inventory before delivery so newly added iPads are included; exclude simulators and Apple Watch. Do not treat installation on one device as delivery to all devices. This is the default for every application update, even when the request mentions only the phone or one iPad; an explicit one-device reinstall request may target only that device. Normal companion app restarts are authorized; preserve drafts and user data. If any device is disconnected, locked, unavailable, or installation/launch is denied, report that device's exact blocker and remaining user action separately, and do not claim its update or verification succeeded. Report build/signature/install/launch verification per device; simulator checks alone are not physical-device delivery.
- For Android, discover all intended physical devices with adb, rebuild and sign with the existing Android setup, and use `FREDDAI_ANDROID_DEVICE=<serial> pnpm android:install` for each device. Relaunch and verify the installed build and running app per device. Preserve app data; do not uninstall to work around signing conflicts. If no authorized physical Android device is available, report that exact delivery blocker and the required connection/unlock/USB-debugging authorization action; a successful APK build or emulator run is not physical-device delivery.
- After installing, relaunch through approved native-app controls and verify the running instance uses the new bundle. Do not assume an already-running process reloads a replaced application. The user authorizes normal app restarts without waiting for active agents to finish or asking for restart permission again. Background agents continue independently of the GUI; interrupted work is expected to recover through the existing restart/resume mechanisms. Verify and report actual recovery rather than claiming an untested macOS reboot will resume every task. Preserve drafts when possible and never force-kill agent processes just to update.
- If native-app control is denied, do not bypass the restriction. State that the installed update is ready but the running instance still needs restarting, with the exact user action needed. Never claim the new version was launched or tested when only installation was verified.
- Keep the spec current. Report source/tests/build/signature/install/launch/live-provider verification separately.
- Do not use accounts, credentials, or live agent turns as test fixtures. Account creation, sign-in, and per-subscription validation must be explicit; never fabricate connected accounts to enable Start.

- Freddai Virtual Office means the desktop dashboard as well as iPhone, every iPad, Android, and browser companions. Keep its rendering in the shared `packages/app/src/office` component whenever possible. Project title signs must not show message, thread, or working counters; use that space for readable project titles on every screen size.
